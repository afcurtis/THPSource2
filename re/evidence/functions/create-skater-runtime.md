## Validation method

Same pattern as Phase 4.8 ([career-runtime.md](career-runtime.md#validation-method)): the probe
`re/gdb/probes/create_calls.py` stops the running game at a physics frame, lays random legal state out in memory,
calls one *retail* function through a GDB inferior call with its outside services stubbed, and records the return
value, the bytes it wrote and the ordered service calls. `src/runtime/create_retail_calls_test.cpp` replays each
case from the same memory image through the native port; all three must match. What 4.9 added:

- **A scratch slab.** The create code works on objects the editor allocates (palettes, texture databases, part
  tables, models). The probe takes one block from the game's own allocator and lays fake objects out in it,
  so every byte a function may touch is inside one captured region; globals stay at their retail addresses.
- **Service stubs that carry data.** `fill=` writes bytes into a caller buffer and records them as scripted dwords
  (the palette read), `blob=` records the bytes a service was handed (the palette store), `result=` scripts a value
  (allocation, file open, scene material lookup, text width).
- **Unspecified bytes.** Records built in locals and copied whole carry stack garbage; the replay skips the bytes the
  native port reports as unspecified (`Adapter::unspecified`).
- **Overlapping pokes are rejected** by the probe: the fixture lists pokes by address, so two pokes over the same
  bytes would replay in another order (a generator bug caught in this milestone).
- **Mutation check.** Changing one recorded byte makes the replay fail (`tests/test_create.py`).

## Custom skater records (create-custom-records)

A custom skater is a 0x80-byte record at `0x0056a488 + slot * 0x80` plus a career record (`0x00568a6c + character *
0x104`, the character `Skater_MapEnabledIndex(slot)` names) holding its stat bytes at +0x38.

| Record field | Meaning |
|---|---|
| +0x00 / +0x10 | name `Skater A`.. / hometown `Woodland Hills` |
| +0x20, +0x21, +0x22, +0x23 | 0x12, spare stat points (5), flag (1), 100 in a new record |
| +0x24 | build 0..2: picks one of three ten-byte stat offset rows (`0x00539e10` points at them) |
| +0x25 | sex 0 or 1 (slot 0 is always 0) |
| +0x26 | valid (0 or 1) |
| +0x27..+0x2a | four colour preset indices (0..0x23) |
| +0x2c | ten stat dwords: points the player allocated |
| +0x54 | the editor's hue dword |
| +0x64 | seven texture-set ids, one per clothing kind |

`CustomSkater_Init` fills the defaults, adds the build's offsets to the career record's stats and moves any point
above 10 back to the spare points (asserting "There should be no overflow"), picks the first texture set of every
kind, then calls `CustomSkater_Randomize`: sex, build, base stats plus offsets, the first set of every kind, then
random steps through the set chains (`TextureSet_Step`) and four random colour presets. The order and limits of
the 14 kinds of `Rnd` calls are replayed through the service log. `CustomSave_CopySlot` copies a record, its staged
appearance (0x58 bytes per slot at `0x0056a6cc`) and its career record into a save image and makes that image
live. The trick database initialisation (`TrickConfig_InitializeCharacter`) is a reported service (4.7b validated it).

## Part database (create-part-database)

`Part_GroupIndex` maps a part name to a body group through four NULL-ended pointer lists at `0x00525db0` (head;
stomach, chest, arms, hands; pelvis, legs, shoes; board, wheels). `MySkater__ClassifyPart` sends pelvis, stomach,
chest and head to slots 0..3 and every other part to the next free slot from 4 (at most 0x13);
`MySkater__BuildPartMap` applies it to a region's visible models (bit 0x20 of a model's first byte hides a part).

## Spool queue and text layout (create-spool-text)

The bitmap spool queue keeps 0x40 entries; a **nonzero flag marks an entry free** (zeroed memory is a queue full of
requests). `Spool_Compact` packs live entries to the front and marks the rest free; `Spool_Add` updates the name
of a matching live request or fills the first free entry. `Text_Layout` breaks a message into lines of at most 500
pixels with the font's width (a service), `&` forces a break, and a word that does not fit moves to the next line
without being consumed (a single word wider than a line would repeat forever; the editor's texts never do).

## Stitching (create-stitch)

Seam vertices come in pairs, a *stitch* vertex (flag bit 0) and a *ghost* vertex (bit 1, its x names the stitch
vertex it mirrors in eighths). `PartStitcher_CopyModels` replaces the build region's models with copies of the
source's visible ones placed by the part map, `PartStitcher_LogStitches` numbers stitch vertices, `PartStitcher_
ReorderStitches` moves each ghost by the change of numbering, `PartStitcher_AddStitch` makes a new pair and
renumbers the ghosts after it. The part map has 0x78 (source, build) pairs; the lookups return -1 for none (the
decompile dropped it). Three seeds of random models are in the fixtures.

## What is not ported

- The two welding functions (`PartStitcher_Weld`, `_WeldPair`) and the stitcher constructor transform vertices by
  the animation pose through the PSX geometry transform (`gte_rt`, `FUN_004f4fe0`): planned `create-stitch-weld`.
- The custom skater object's lifecycle and texture application (constructor, destructors, the part-manifest
  readers, the checksum collectors over PSX model tables, applying a texture set to a part, region creation, the
  whole-skater builders): planned `create-skater-objects`. They need the PSX region and material tables and the
  object allocator modelled.
- The editor, select / load / save and stat editor windows: planned `create-editor-ui`, on the 4.10 toolkit
  ([create-editor-ui.md](create-editor-ui.md)).
- A full database (0x100 textures), a full set table through `LoadCretex` and the "too many parts" paths of the
  stitcher are not exercised; neither is a natural play-through of the editor (states are generated).
